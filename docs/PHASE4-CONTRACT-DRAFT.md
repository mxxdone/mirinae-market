# Phase 4 주문·결제 계약 초안

상태: 사용자 확인 대기. 미정 사항을 구체화한 제안이며 확정된 구현 계약이 아니다. 확인 후 docs/SPEC.md에 통합하고 이 초안은 제거한다.

## 목적·범위

한 시장의 여러 매장 상품을 장바구니에 담아 전체 재고를 확보하고 한 번의 모의 결제로 확정한다. 구매자 장바구니·결제·본인 통합/매장 주문 내역을 연결한다. Phase 5의 일반 취소·판매 실패·수령, 실결제는 제외한다.

## 제안 1 — 재고와 판매자 수정

- 온라인 수량은 새 주문에 제공할 수 있는 잔여 판매 단위 수다. 재고 확보 시 즉시 차감하고 확정 시 다시 차감하지 않는다. 실패·만료가 확정되면 확보량을 한 번만 반환한다. 중단·삭제된 상품은 반환해도 재공개하지 않는다.
- 판매자 수량 변경은 조회한 재고 버전을 함께 제출한다. 주문 확보·반환·수량 변경 때마다 버전을 올리고 오래된 수량 입력은 409로 전체 미적용한다. 예시: 잔여 10개 조회 후 주문이 2개 확보하면 잔여 8개가 된다. 이전 버전으로 10개를 저장하면 거절하고 새로 조회하도록 안내한다.
- 가격 변경은 이후 확보에만 적용한다. 판매 중단·상품 삭제는 신규 확보를 막지만 이미 확보한 결제와 확정 주문은 유지한다.
- 유효한 확보 또는 확정 주문이 있는 매장·날짜의 주문 마감·수령 시간 변경은 409로 거절한다. 동일 시간 재저장은 허용한다. 실패·만료로 모든 확보가 해제되고 확정 주문이 없으면 기존 마감 전 변경할 수 있다.
- 매장 여러 곳의 잠금은 매장 ID 오름차순으로 획득한다. 확보·반환과 기존 판매 저장은 같은 매장 잠금에 참여한다. 모의 결제 응답을 기다리는 동안 DB 트랜잭션·매장 잠금을 유지하지 않는다.

## 제안 2 — 가격 확인·확보·마감

- 장바구니는 구매자 계정별 서버 저장이며 시장 하나·수령일 하나에 최대 100개 서로 다른 판매 제안을 담는다. 수량은 판매 단위의 양의 정수다. 다른 시장 상품을 추가하면 기존 장바구니 비우기 확인을 요구한다. 장바구니 담기 자체는 재고 확보가 아니다.
- 결제 요청은 장바구니 버전과 구매자가 확인한 상품별 가격·매장별 시간을 제출한다. 서버는 잠금 획득 후 당일·시장·활성 판매·미삭제 상품·모든 매장 마감·재고·가격·시간을 재검사한다.
- 가격 또는 시간이 바뀌면 전체 확보 없이 변경 내용을 409로 반환한다. 구매자가 변경 조건을 확인한 새 요청으로만 진행한다. 하나라도 판매 중단·삭제·날짜 경과·마감·품절이면 전체 확보와 결제를 시작하지 않는다.
- 확보 유효 시간은 확보 시점부터 최대 5분이며 포함 매장의 가장 이른 주문 마감까지만 유효하다. 만료 시각과 마감 정각은 유효 범위에서 제외한다. 결제 성공의 기준은 모의 결제 제공자가 저장한 승인 시각이다.
- 마감·자정 전에 유효하게 승인된 결제는 응답이 늦어져도 확정한다. 만료 정각 이후 승인은 주문을 확정하지 않고 모의 결제를 취소/전액 환불한 뒤 확보를 해제한다. 확보 후 변경된 판매 가격을 주문에 적용하지 않는다.
- 상품명·구성·단가·수량·매장명·시장·수령일·주문 마감·수령 시간을 주문 스냅샷에 보존한다. 총액은 원화 정수의 64비트 합계로 계산한다. 이후 중단·삭제·가격 변경이 주문 내역을 바꾸지 않는다.

## 제안 3 — 중복·실패·응답 유실

- 구매자별 요청 키로 결제를 식별한다. 같은 키·같은 요청은 기존 결과를 반환하고 다른 내용이면 409다. 동시 중복에도 주문·차감·모의 결제는 한 번만 생성한다. 동일 장바구니 버전에 진행 중인 결제는 하나만 허용한다.
- 확보와 결제 준비 기록은 같은 DB 트랜잭션에 저장한다. 모든 상품 확보에 성공해야 커밋한다. 확정 시 통합 주문·매장 주문·상품은 함께 저장한다. 다른 구매자의 결제·주문 조회는 거절한다.
- 모의 결제는 성공·명시적 실패·지연·승인 후 응답 유실을 재현한다. 모의 제공자는 요청 키별 결과를 저장하고 같은 키 재호출/조회로 중복 승인되지 않는다. 응답 유실 시 화면은 결과 확인 중을 표시하고 같은 결제의 상태를 조회한다.
- 결과를 모르면 재고를 즉시 반환하지 않는다. 복구 처리가 저장된 결제 결과를 조회하고, 기한 내 성공이면 확정하며 실패이면 해제한다. 기한이 지나도 먼저 제공자의 승인 여부를 확인하고 미승인 요청을 취소 상태로 닫는다. 늦은 승인은 보상 완료 후 해제한다.
- 서버 재기동 후에도 DB에 남은 진행 결제를 복구한다. 복구·사용자 재조회가 동시에 실행돼도 확정·반환·보상은 한 번만 수행한다. 보상 실패는 복구 대기 상태를 유지하며 성공할 때까지 재시도한다. 확인되지 않은 결제는 성공·실패로 단정하지 않는다.

## 핵심 수용 기준

- Given 같은 시장 두 매장의 유효 상품 / When 구매자가 확인 가격으로 결제 / Then 전체 확보 후 한 통합 주문·두 매장 주문을 확정하고 내역에 스냅샷을 표시한다.
- Given 장바구니 수량 수정·로그아웃 / When 다시 로그인 / Then 본인 서버 장바구니를 조회하며 로그아웃 중 개인 정보를 화면에 남기지 않는다.
- Given 한 상품 재고 부족 / When 여러 상품 확보 / Then 전체 미적용하며 부족 상품을 알려주고 결제 기록을 승인하지 않는다.
- Given 마지막 재고 1개 / When 서로 다른 구매자가 동시에 확보 / Then 한 요청만 확보하고 음수 재고·초과 확정이 없다.
- Given 담은 후 가격·수령 시간 변경 / When 이전 조건으로 결제 / Then 전체 차감 없이 변경 내용을 안내하고 재확인 전 결제하지 않는다.
- Given 판매 중단·삭제·다른 시장·수령일 경과·매장 마감 / When 결제 시작 / Then 해당 항목을 안내하고 전체 미진행한다. 마감 정각도 거절한다.
- Given 잔여 10개를 조회한 판매자와 2개 확보 주문 / When 이전 버전으로 판매 수량 저장 / Then 일괄 변경 전체 409이고 잔여 8개를 덮어쓰지 않는다. 반대 잠금 순서에서는 판매 저장 후 최신 재고로 확보한다.
- Given 확보 또는 확정 주문 / When 공통 시간을 변경 / Then 전체 미적용하며 기존 주문 조건을 보존한다. 동일 시간 저장은 성공한다.
- Given 유효 확보 후 판매 중단·상품 삭제 / When 기한 내 모의 결제 승인 / Then 기존 확보를 확정하며 신규 확보는 거절한다.
- Given 명시적 결제 실패 또는 승인 없는 만료 / When 복구 / Then 주문 미확정·확보량 한 번 반환이며 중단 상품은 중단 상태를 유지한다.
- Given 같은 요청 키의 동시 재시도 / When 결제 / Then 하나의 결제·주문·차감만 존재한다. 다른 요청 내용은 409다.
- Given 결제 승인 뒤 응답 유실·서버 재기동 / When 같은 결제 조회와 복구 / Then 같은 승인 결과로 한 주문만 확정한다.
- Given 만료 전 승인·자정 뒤 응답 / When 복구 / Then 승인 시각을 기준으로 원래 수령일 주문을 확정한다. 만료 정각 이후 승인은 보상 후 재고를 해제하고 주문은 확정하지 않는다.
- Given 보상 실패 / When 복구 재실행 / Then 확인 중 상태와 확보를 유지하고 중복 환불 없이 성공 후 한 번 해제한다.
- Given 다른 구매자 또는 판매자 계정 / When 구매자 장바구니·결제·주문 변경/조회 / Then 해당 역할·본인 권한과 CSRF 계약에 따라 거절한다.

## 영향·호환성과 구현 순서

- 판매 조회에 재고 버전을 추가하고 수량 저장에 버전을 요구하므로 기존 단건·일괄 API, 판매 표, OpenAPI와 관련 테스트를 함께 바꿔야 한다. 기존 가격·마감·삭제 정책은 위 변경 범위 외에는 유지한다.
- DB 마이그레이션은 기존 V1~V5를 수정하지 않고 추가한다. 주문·확보·결제 결과·장바구니 영속성을 검증한다. 적용 전 백업·별도 DB 복원 검증을 하고 이전 앱 복구는 서비스 중지와 적용 전 백업 복원으로 수행한다.
- 모듈 간 호출은 공개 Business 진입점만 사용한다. 재고는 product 모듈이 소유하고 checkout 모듈이 공개 진입점으로 사용한다. product는 checkout을 역참조하지 않는다. 결제 제공자 상태는 Data에 격리한다. 정확한 테이블·API·복구 주기와 상태명은 계약 확인 후 ADR·OpenAPI에 기록한다.
- 계약 확인 후 핵심 규칙 TDD → 실제 PostgreSQL/HTTP·동시성/재기동 검증 → 장바구니·결제·내역 UI → 자체 백엔드 포함 E2E → 필수 gate·diff 리뷰 순으로 진행한다. 이 초안 작성은 기능 완료나 검사 통과를 의미하지 않는다.
