# 미리내 마켓 Spec

상태: 핵심 도메인·기술 스택 합의 완료. 기능별 세부 계약은 구현 전에 보완하며 미정 항목은 구현 계약으로 사용하지 않는다.

## 목적과 범위

- 전통시장 방문 전에 매장별 예약 가격을 비교하고, 온라인 선결제로 상품을 확보해 당일 매장에서 수령한다.
- 판매자는 컴퓨터 또는 스마트 기기를 사용할 수 있는 시장 점포 운영자다.
- 포트폴리오·학습 목적이며 빠른 구현을 지향한다. 실제 운영·실결제는 제외한다.
- 백엔드는 Java·Spring을 사용한다. 세부 기술은 도메인과 검증 목표 확정 후 결정한다.
- 백엔드 API·업무 규칙·검증을 먼저 구현하고 구매자·판매자 프런트엔드는 나중에 별도 연결한다. 동작하는 기준 백엔드를 확보한 뒤 부하 테스트와 측정 결과에 근거한 성능 개선을 진행한다. 화면 시연은 프런트엔드 연결 후 완성한다.
- 판매자 주문 관리 화면의 카운트 집계 성능과 정확성 검증을 포트폴리오 주제로 삼는다. 외부 사례의 성능 수치는 프로젝트 실측 결과로 사용하지 않는다.

## 확정된 도메인과 업무 규칙

### 시장과 주문 구성

- 여러 시장을 등록할 수 있다. 구매자는 한 시장을 선택한 뒤 품명으로 검색하고 점포별 가격을 비교한다.
- 같은 시장의 여러 점포 상품을 한 번에 결제할 수 있다.
- 통합 결제 내부에는 매장별 주문이 존재한다. 수령·판매 실패·미수령·환불은 매장별로 처리하며 다른 매장 주문을 변경하지 않는다.

### 예약과 가격

- 당일 주문·당일 수령만 지원한다.
- 주문과 일반 구매자 취소는 매장·수령일별 주문 마감 전에만 가능하다. 판매자는 분 단위 주문 마감을 지정하며 수령 시작보다 늦을 수 없다. 정각부터 마감한다.
- 판매자는 수령할 날짜의 예약 가격과 온라인 판매 가능 수량을 등록한다.
- 결제한 주문의 가격은 고정한다. 가격 변경은 이후 주문에만 적용한다.
- 가격 변동에 따른 추가 결제·차액 환불은 하지 않는다. 구매 전 가격 고정 정책을 표시한다.

### 재고와 결제

- 판매자는 이미 확보한 실물 재고 중 온라인으로 제공 가능한 수량을 등록하고, 주문 확정분은 현장 판매하지 않도록 따로 보관한다. 도매 매입·납품과 현장 POS·실물 재고 자동 연동은 범위 밖이다. 앱은 등록된 온라인 수량을 넘는 주문을 막는다.
- 실결제 대신 구매·결제 요청을 모의 결제 연동으로 처리한다. 모의 환불을 지원한다.
- 결제 성공 시 판매자 수락 대기 없이 주문을 확정한다.
- 결제 전에 통합 주문에 포함된 모든 상품의 재고를 확보한다. 하나라도 부족하면 전체 주문·결제를 진행하지 않고 부족한 상품과 장바구니 수정 안내를 표시한다.
- 장바구니에 담은 뒤 가격이 바뀌었으면 변경 가격을 표시하고 구매자가 다시 확인해야 결제를 진행한다. 장바구니에 담았을 때의 가격 보장은 하지 않는다.
- 결제 진행 중 재고 확보 시점·만료·실패 보상·중복 요청 규칙은 미정이다.

### 수령과 판매 실패

- 한 매장 주문의 유효한 상품은 한 번에 수령한다. 같은 매장 내 상품별 분할 수령은 제외한다.
- 판매자가 제공하지 못하는 상품은 해당 상품만 즉시 취소·모의 환불하고 사유를 주문 화면에 표시한다.
- 판매 실패가 발생한 매장 주문은 구매자가 나머지도 취소하거나 나머지를 수령할 수 있다.
- 나머지 취소는 수령 완료 또는 수령 마감 전까지만 가능하다. 이 예외는 해당 매장의 일반 취소 마감 이후에도 적용된다.
- 구매자가 선택하지 않으면 나머지 주문은 유지한다. 다른 매장 주문에는 영향이 없다.
- 구매자 책임의 미수령은 미수령 처리하며 자동 환불하지 않는다. 첫 버전에서 미수령에 따른 이용 제한은 제외한다.
- 매장이 날짜별 수령 시작·마감 시간을 지정한다. 구매자는 결제 전에 매장별 수령 시간을 확인한다.
- 매장 주문별 수령 코드를 발급하고 판매자가 구매자의 코드를 입력해 수령을 확인한다.

### 판매자 대시보드

- 판매자는 자신의 매장 데이터만 조회한다. 주문 건수는 통합 결제 건수가 아닌 매장별 주문 건수다.
- 수령일별 주문 수, 미수령·수령 완료·전체 취소 건수, 상품별 준비 수량을 표시한다. 일부 상품 취소·환불은 전체 취소와 구분해 표시한다.
- 누적 주문 수와 중복 제외 구매자 수를 표시한다.
- 누적·월별 주문 금액은 결제 총액·환불액·환불 차감 후 금액을 구분해 표시한다. 모의 결제 금액이며 실제 정산·매출 인식 기능은 아니다.
- 첫 구현에서는 모든 지표를 원본 데이터에서 정확하게 조회한다. 조회 후 발생한 변경까지 실시간으로 화면에 반영해야 한다는 의미는 아니다.
- 지연 집계·캐시를 선제 도입하지 않는다. 성능 측정 후 필요한 지표의 최신성 요구 변경과 개선 방안을 검토한다.
- 월별 귀속 날짜와 각 상태·구매자 집계 대상의 세부 정의는 구현 계약 확정 시 보완한다.

## 상품 범위와 미정 사항

- 대상 상품군: 해산물·농축산물 등.
- 상품은 판매자가 직접 등록한다. 과일은 개수 기준, 무게로 판매하는 상품은 중량 기준으로 등록할 수 있다.
- 개수·고정 중량 포장을 모두 지원한다. 상품별 포장 가격과 단위당 보조 가격을 보여주며 자동 동일 상품 묶기·동일 규격 판정·가격 정렬은 제공하지 않는다. 판매자가 표시 중량을 충족하는 포장을 준비하고 결제 후 무게에 따른 금액 정산은 하지 않는다.
- 판매자는 한 판매 단위의 구성과 가격을 등록하며 구매자는 판매 단위 수량을 양의 정수로 선택한다.
- 예: 새우 500g 봉지 × 2는 500g 봉지 2개, 사과 1박스(12개) × 2는 12개들이 박스 2개다. 재고는 판매 단위 개수로 관리한다.
- 중량은 내부적으로 g로 저장하고, 한 판매 단위의 중량은 100g의 양의 정수 배수여야 한다. kg 입력은 g로 변환한다.
- 상품명은 판매자가 자유롭게 작성하고 중량·개수는 별도 숫자 필드로 입력한다. 검색·단위당 가격 표시 계약은 Phase 3 항목을 따른다.
- 구매자 가입을 구현한다. 판매자·시장·매장은 데모 데이터로 제공하며 판매자 가입 신청·관리자 승인 기능은 첫 버전에서 제외한다.
- 구매자와 데모 판매자는 계정으로 로그인한다. 인증은 세션 기반이며 OAuth2·JWT·Redis 토큰 관리와 소셜 로그인은 첫 버전에서 제외한다.
- 가격 변경 중 결제의 기준 시점, 결제 부분 실패, 환불 실패·재시도와 주문 상태 전이는 미정이다.
- 구체적인 부하 테스트 조건은 시연 흐름 완성 후 기준 성능 측정 단계에서 정한다.

## Phase 2 — 계정·권한 계약

### 가입과 계정

- 구매자 가입 입력은 로그인 ID, 비밀번호, 표시 이름, 이메일이다. 역할은 서버가 BUYER로 지정하며 판매자 가입·역할 변경은 제공하지 않는다.
- 로그인 ID는 5~20자의 영문 소문자·숫자·밑줄(_)·하이픈(-)만 허용한다. 입력을 자동으로 잘라내거나 대문자를 소문자로 바꾸지 않는다. ID는 유일하며 로그인 식별자로 사용한다.
- 표시 이름은 2~10자의 완성형 한글·영문 대소문자·숫자만 허용한다. 한글·영문 모두 한 글자를 한 자로 세며 공백·이모지·특수문자는 허용하지 않는다. 표시 이름은 중복 가능하다. 이 제한은 실제 사용자 입력·표시 규칙이며 DB 저장 용량만의 제한이 아니다.
- 비밀번호는 8~32자의 공백 없는 ASCII 문자로, 영문·숫자·특수문자를 각각 하나 이상 포함해야 한다. 영문 대소문자를 구분하고 입력을 trim·정규화·잘라내지 않는다. 저장·응답·로그에 평문을 남기지 않는다.
- 이메일은 필수이며 일반적인 ASCII 이메일 형식과 최대 254자 길이를 검증한다. 앞뒤 공백 제거와 Locale.ROOT 소문자화 후 저장·중복 검사한다. 이메일을 로그인 ID로 사용하지 않는다.
- 동일 ID 또는 정규화한 이메일의 중복 가입은 409로 거절한다. 동시에 같은 계정으로 가입해도 하나만 저장한다. 입력 규칙 위반은 400이며 실패 시 계정을 남기지 않는다.
- 이메일 소유 확인·메일 발송·비밀번호 재설정은 이번 범위에 포함하지 않는다. 입력 이메일은 미인증 정보이며 인증·계정 복구·소셜 계정 자동 연결의 근거로 사용하지 않는다. 전화번호는 방문 수령·모의 결제의 현재 흐름에 쓰이지 않으므로 수집하지 않는다.
- 계정의 내부 식별자는 로그인 ID·이메일과 독립적으로 유지한다. 향후 OAuth2 연동 시 제공자와 제공자 사용자 식별자로 연결하고 기존 계정 연결에는 별도의 소유 확인이 필요하다. 이번 페이즈에는 OAuth2 코드·테이블을 선제 생성하지 않는다.

### 로그인·세션과 권한

- 역할은 BUYER와 SELLER 중 하나다. 판매자 계정 하나가 매장 하나를 소유하고, 매장에는 판매자 소유자 하나와 소속 시장 하나가 있다.
- 로그인은 ID·비밀번호로 서버 세션을 생성한다. 잘못된 ID와 비밀번호는 동일한 401 응답이며, 성공 시 세션 식별자를 교체한다. 가입 직후 자동 로그인하지 않는다.
- 세션 쿠키는 HttpOnly·SameSite=Lax, 유휴 만료는 30분이다. 로컬 HTTP 실행에서는 Secure=false이며 HTTPS 환경에서는 설정으로 Secure=true를 사용한다. 쿠키 이외 URL 세션 식별자는 허용하지 않는다.
- CSRF는 가입·로그인·로그아웃을 포함한 변경 요청에 적용한다. 미인증 상태에서도 CSRF 토큰을 받을 수 있고, 로그인·로그아웃 후 토큰을 다시 조회한다. 토큰 누락·오류는 403이다.
- 미로그인 보호 자원 접근은 401, 다른 역할·다른 매장 접근은 403이다. 권한은 서버에서 검사하며 매장 소유권 실패 시 매장 정보를 반환하지 않는다.
- 로그아웃은 세션 무효화와 쿠키 삭제를 수행한다. 이전 쿠키로 현재 사용자를 조회하면 401이다. 현재 사용자 응답에는 내부 ID·로그인 ID·표시 이름·역할을 제공하고 비밀번호·해시는 제공하지 않는다.

### 데모와 백엔드 검증 범위

- 데모 시장 두 개와 매장·판매자 각각 두 개를 준비해 다른 시장·다른 매장 접근을 검증한다. 데모 구매자 하나도 제공한다. 계정별 이메일은 example.com 데모 주소를 사용한다.
- 데모 데이터는 demo 프로필에서만 재현 가능하게 생성하고 재기동 시 중복 생성하지 않는다. 기본 프로필의 스키마 마이그레이션에는 데모 계정·비밀번호를 넣지 않는다.
- 백엔드 API 계약: POST /api/accounts (JSON 가입, 201), POST /api/auth/login (폼 loginId/password, 200), POST /api/auth/logout (204), GET /api/auth/me (현재 사용자), GET /api/auth/csrf (토큰·헤더 이름), GET /api/seller/stores/{storeId} (본인 매장 조회). 인증·인가 실패는 리다이렉트 대신 JSON 상태 응답을 사용한다. 오류 응답은 한국어 설명과 안정적인 오류 코드를 제공한다.
- Phase 2 프런트엔드는 구매자 가입·가입 완료·로그인·계정 요약과 판매자 본인 매장 조회를 제공한다. 실제 PostgreSQL·서버와 브라우저 쿠키·CSRF 흐름으로 검증한다. 상품·주문 기능은 후속 페이즈 범위다.
- 판매자는 로그인과 세션 복원 후 본인 점포 화면에 진입한다. GET /api/seller/stores/me는 서버 세션의 계정으로 담당 점포를 찾아 반환하며 매장 번호 입력을 요구하지 않는다. 기존 점포 고유번호·소유 관계를 사용하며 한 판매자당 한 매장 정책을 유지한다. 미로그인은 401, 구매자 또는 담당 매장 없는 판매자는 403이다. 기존 번호 지정 조회 API도 소유권 검사를 유지한다.

### Phase 2 화면 수용 기준

- Given 유효한 가입 정보 / When 화면에서 가입함 / Then 자동 로그인 없이 가입 완료를 표시하고 로그인 화면에 ID만 인계하며 비밀번호는 비운다.

## Phase 3 — 상품·판매 제안 계약

### 확정된 판매 단위 수용 기준

- Given 중량 판매 단위 / When 100g·500g·1000g처럼 100g의 양의 정수 배수로 구성함 / Then 단위 중량을 g로 유지하고 허용한다.
- Given 중량 판매 단위 / When 0 이하 또는 100g 배수가 아닌 중량으로 구성함 / Then 입력을 거절하고 다른 중량으로 자동 보정하지 않는다.
- Given 개수 판매 단위 / When 1개 또는 12개처럼 양의 정수로 구성함 / Then 판매 단위 하나에 포함된 개수를 유지한다.
- Given 개수 판매 단위 / When 0 이하의 개수로 구성함 / Then 입력을 거절한다.
- Given 판매 단위 / When 중량·개수 방식이 지정되지 않음 / Then 입력을 거절한다.

### 상품·조회 계약

- 상품명은 앞뒤 공백을 제거한 1~100자 자유 입력이며 제어 문자는 허용하지 않는다. 상품명에서 중량을 추출하거나 표준 품목으로 자동 연결하지 않는다. 설명은 선택이며 앞뒤 공백 제거 후 최대 1,000자다.
- 판매 구성은 unitType(WEIGHT 또는 COUNT)와 unitAmount(정수)로 별도 입력한다. WEIGHT는 g, COUNT는 한 판매 단위에 포함된 개수다. JSON 소수 입력을 정수로 잘라내지 않고 400으로 거절한다.
- 상품명·판매 구성은 판매 제안이 없을 때 수정할 수 있다. 판매 제안이 생성된 후 변경하려면 새 상품을 등록한다(409 PRODUCT_LOCKED). 설명은 수정할 수 있다. 단건 삭제는 기록을 보존하고 판매자 목록·현재 공개 판매에서 제외한다. 상품과 기존 판매 제안은 물리 삭제하지 않으며 삭제한 상품의 수정·재공개는 404다. 본인 상품 삭제 재요청은 204이며 기존 주문 취소와 별개다.
- 시장 목록·오늘 수령 상품 검색·상품 상세는 로그인한 구매자·판매자가 조회한다. 검색은 해당 시장의 상품명에 검색어가 포함되는지 확인하며 영문 대소문자를 구분하지 않는다. %, _는 일반 문자이고 최대 100자다. 빈 검색어는 전체 조회다.
- 한 페이지는 1~100건이며 기본 20건이다. 페이지는 0부터 시작하고 offset이 정수 범위를 넘으면 400이다. 고정 ID순과 hasNext를 제공한다. 자동 동일 상품 묶기·가격 정렬은 제외한다.
- 포장 가격은 원화 정수이며 1~2,147,483,647원이다. 보조 비교 가격은 WEIGHT의 경우 100g당, COUNT의 경우 1개당 가격이며 소수 둘째 자리까지 반올림한다. 비교 가격은 표시용이고 결제 가격으로 사용하지 않는다. 원산지·등급·품종 등이 같은 상품이라는 보장은 하지 않는다.

### 오늘 판매 등록

- 날짜 판단은 Asia/Seoul 기준이다. 수령일은 등록·수정 시점의 오늘만 허용한다. 다음 날 판매는 자동 재공개하지 않으며 판매자가 가격·제공 수량을 확인해 수동 공개한다. 저장하면 별도 승인 없이 즉시 구매자 조회에 표시한다.
- 상품 기본 정보와 날짜별 판매 조건을 분리한다. 같은 상품·수령일의 판매 조건은 하나이며 재등록은 기존 가격·온라인 수량을 수정한다. 온라인 수량은 판매 단위 개수로 0~2,147,483,647이며 0은 품절로 표시한다. 현장 재고는 관리하지 않는다.
- 수령 시간은 같은 매장·수령일에 하나를 공유한다. 통합 판매 표는 공통 시간과 상품별 조건을 일괄 적용한다. 기존 단건 판매 API를 사용할 때는 먼저 공통 시간을 등록해야 하며 시간이 없으면 409 PICKUP_WINDOW_REQUIRED다.
- 수령 시작·마감은 같은 날의 분 단위 시각이며 시작 < 마감이어야 한다. 날짜를 넘는 시간대는 제공하지 않는다.
- 주문 마감은 수령 시작보다 늦을 수 없다. 신규 시간 저장 시 현재 시각보다 늦은 주문 마감만 허용한다. 기존 시간은 기존 주문 마감 전에만 변경할 수 있고 새 마감도 현재보다 늦어야 한다. 가격·온라인 수량은 해당 매장의 주문 마감 전에만 수정한다. 마감 정각 또는 날짜가 지난 조건은 검색·상세에 공개하지 않는다. 본인 매장 시간 조회는 당일 마감 후에도 허용한다. 상품 자체는 이후 수령일에 다시 사용할 수 있다.
- 등록·수정은 판매자 역할과 매장 소유권을 서버에서 검사한다. 미로그인은 401, 구매자·다른 매장은 403이고 데이터가 변경되지 않는다. 본인 매장 내 없는 상품·공개 범위 밖 상세는 404 NOT_FOUND다.
- 주문은 아직 구현하지 않는다. 주문 이후 수량·시간 변경 제한과 재고 확보 정책은 Phase 4에서 확정하며 이번 등록 API를 주문 동시성 검증으로 표현하지 않는다.

### API와 수용 기준

GET /api/seller/stores/{storeId}/products/{productId}: 본인 미삭제 상품 조회, 없는 상품·삭제 상품은 404. PUT /api/seller/stores/{storeId}/products/{productId}: 상품 수정. DELETE 같은 경로: 이력을 보존하는 단건 삭제(204).
- GET /api/seller/stores/{storeId}/pickup-windows/{pickupDate}: 오늘의 저장된 본인 매장 수령 시간(미등록 404). PUT /api/seller/stores/{storeId}/pickup-windows/{pickupDate}: 매장 수령 시간 등록·수정. PUT /api/seller/stores/{storeId}/products/{productId}/offers/{pickupDate}: 날짜별 판매 조건 등록·수정(200).
- Given 양파 3kg 상품과 별도 WEIGHT·3000 입력 / When 9,000원·20포장으로 오늘 판매 등록 / Then 실제 DB에 저장되고 해당 시장에서 포장 가격 9,000원·100g당 300.00원이 표시된다.

- Given 매장 주문 마감 직전·정각 / When 당일 판매 조건을 등록·수정 / Then 직전은 허용하고 정각부터 400으로 거절하며 공개 검색·상세에서 제외된다. 자정부터 검색 날짜는 새 오늘로 바뀌지만 기존 상품은 자동 재공개되지 않는다.
- Given 저장된 판매 조건 / When 재등록 또는 매장 수령 시간을 수정 / Then 같은 제안 ID를 유지하고 같은 매장·날짜의 모든 상품에서 공통 수령 시간이 표시된다.
- Given 가격 0·음수 수량·소수 입력·잘못된 중량·역전/동일 수령 시간 / When 등록·수정 / Then 400이고 기존 데이터는 그대로다.
- Given 판매 제안이 있는 상품 / When 상품명·판매 구성을 변경 / Then 409이며 원래 정보가 유지된다. 설명만 변경하면 성공한다.
- Given 미로그인·구매자·다른 매장 판매자·CSRF 누락 / When 판매자 변경 API 요청 / Then 401 또는 403이며 저장·수정하지 않는다.

### Phase 3 화면 수용 기준

- 구매자 목록과 판매자 상품 표는 번호 페이징을 사용하며 현재 페이지를 강조한다. 두 목록은 20개씩 조회한다. 판매 관리 표의 통합 계약은 아래 일괄 판매 수용 기준을 따른다.
- 공개 상품 목록의 totalItems는 같은 시장·검색어·당일·주문 마감·상품 삭제·판매 활성 조건을 적용한 총건수다. 기존 page·size·hasNext 응답은 유지한다.

- Given 상품 목록에서 검색 후 상세를 엶 / When 브라우저 뒤로·앞으로 또는 목록으로 버튼을 사용함 / Then 목록·상세를 전환하고 시장·검색어·페이지를 유지한다. 로그인 세션이 유효하면 상세 URL 새로고침도 상세를 복원한다.
- Given 로그아웃·세션 만료 / When 브라우저 방문 기록 또는 상세 URL에 접근함 / Then 보호 화면을 복원하지 않고 로그인을 안내한다. URL·방문 기록에는 상품 식별자와 검색 조건만 저장하며 계정·API 응답·인증 정보는 저장하지 않는다.

- Given 담당 매장이 있는 판매자 / When 로그인해 상품을 등록함 / Then 매장은 자동 조회하고 자유 상품명과 판매 구성 숫자를 별도 입력한다. g·kg 선택을 지원하며 3kg는 소수 잘라내기 없이 3000g로 전송한다.
- Given 잘못된 중량·개수·가격·온라인 수량 / When 저장함 / Then 입력을 거절하고 오류와 입력을 유지하며 성공 안내를 표시하지 않는다.
- Given 저장된 매장 수령 시간과 판매 조건 / When 판매 관리 화면을 새로고침함 / Then 실제 서버 값으로 공통 시간과 상품 행의 판매 여부·가격·수량을 복원한다.
- Given 오늘 판매 등록이 성공함 / When 구매자가 시장을 선택해 검색하고 상세를 엶 / Then 상품·매장·판매 구성·포장 가격·단위당 보조 가격·수령 시간·온라인 수량을 표시한다.

### 통합 표·일괄 판매 수용 기준 · 2026-10-13

이 계약은 이전 판매자 세 탭·단건 판매·카드 UI 수용 기준을 대체한다. 상품 등록·수정·삭제, 단위 환산과 매장 정보 별도 화면 정책은 유지한다.

- 판매 관리에 중복 제목을 표시하지 않는다. 상품 정보·오늘 판매 탭과 상품별 큰 카드를 제거한다. 등록된 상품의 판매 체크·상품명/규격·포장 가격·온라인 수량·현재 상태·수정을 한 표로 제공한다. 모바일은 같은 행을 두 줄로 표시한다.
- 상품 추가와 수정은 별도 입력 화면으로 이동하고 저장 후 표로 돌아온다. 판매를 자동 시작하지 않는다. 삭제는 수정 화면 하단의 단건 확인으로 처리한다.
- 매장 공통 주문 마감·수령 시간을 한 곳에서 편집하며 변경 사항 적용 한 번으로 공통 시간과 수정한 상품을 한 트랜잭션에 저장한다. 변경 요청은 최대 100행, 중복 상품 ID는 거절한다. 미수정 상품은 그대로 유지한다.
- 적용 전에는 체크·가격·수량·시간 변경을 공개하지 않는다. 이미 판매 중인 상품의 체크 해제 후 적용은 오늘 판매만 중단한다. 상품·판매 행·가격·수량·판매 이력을 보존한다. 중단 상품은 공개 검색·상세·총건수에서 제외한다. 수량 0은 판매 체크를 유지하는 품절이며 공개 목록에 남는다.
- 중단 상품을 다시 체크하고 적용하면 같은 상품·날짜의 기존 제안 ID를 재사용해 공개한다. 마감·날짜·인가 규칙은 기존과 같다. 기존 주문 자동 취소는 포함하지 않는다.
- GET /api/seller/stores/{storeId}/sales/{pickupDate}: 미판매·중단·품절·마감 여부와 무관하게 본인 미삭제 상품 및 오늘 판매 상태를 ID순 페이지로 조회한다. 공통 시간은 기존 본인 시간 조회를 사용한다.
- PUT /api/seller/stores/{storeId}/sales/{pickupDate}: 공통 시간과 변경한 행 products를 한 번에 저장한다. 성공 204. 행 오류는 400 SALE_BATCH_INVALID 및 issues(productId,message)를 반환하며 전부 미적용한다. 공통 시간·날짜 오류는 400 INVALID_INPUT, 인증 401, 역할·매장 소유권 403, CSRF 403이다.
- Given 유효한 공통 시간과 여러 상품 변경 / When 한 번 적용함 / Then 모두 반영하고 실제 서버 성공 후 완료를 표시한다.
- Given 한 상품 가격·수량 오류, 중복 ID, 삭제·다른 매장 상품 / When 적용함 / Then 시간·다른 상품·판매 중단을 포함해 모두 반영하지 않고 오류 행을 알려준다. 해당 매장의 상품 여부 외 타 매장 정보는 노출하지 않는다.
- Given 공개 상품의 체크 해제 / When 적용함 / Then 구매자 목록·상세에서 제외되고 같은 판매 행과 상품 이력은 유지된다. 재공개는 동일 제안 ID다.
- Given 여러 페이지에서 작성한 변경 / When 페이지 또는 매장 정보 화면을 이동함 / Then 작성값과 변경 건수를 유지한다. 보이지 않는 미수정 상품을 중단하지 않는다.
- Given 저장 실패·통신 실패 / When 응답을 받음 / Then 성공 표시 없이 입력을 유지한다. 전송 결과를 알 수 없는 경우 재조회는 명시적인 작업으로 제공하며 자동 재전송하지 않는다. 자정 후 이전 날짜의 작성값을 새 날짜로 조용히 전송하지 않는다.
