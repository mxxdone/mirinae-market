# 설계 결정

## ADR-001 · 2026-10-11 · 기능 모듈별 3계층 단일 서버

- 상태: 채택
- 맥락·제약: 빠른 시연 구현과 주문·재고·환불 정확성 검증이 우선이며, 대시보드 집계 성능은 원본 조회에서 출발해 실측한다.
- 대안: 서비스 분리와 메시지 기반 연동, 단일 서버의 기능 모듈 구성.
- 결정·이유: Java 21·Spring Boot 단일 서버에서 기능별 Presentation → Business → Data 구조를 사용한다. 단일 저장소의 거래 처리를 먼저 검증하며, Redis·큐·복제 DB는 병목 확인 전 도입하지 않는다.
- 단점·재검토 조건: 모듈 간 의존성과 공통 DB 접근이 커질 수 있다. 실제 측정에서 배포·처리 독립성 필요가 확인되면 경계를 재검토한다.
- 요구사항: [Spec](../SPEC.md). 검사·파일 구조는 AGENTS.md와 프로젝트 설정을 따른다.

## ADR-002 · 2026-10-11 · PostgreSQL 원본 저장소와 JPA 기반 영속성

- 상태: 채택
- 맥락·제약: 주문·재고의 거래 일관성과 집계 쿼리의 실행 계획·정확성·성능을 실제 DB에서 검증해야 한다. 사용자는 추천 스택에 동의했다.
- 대안: PostgreSQL과 MySQL, JPA 중심 접근과 직접 SQL 중심 접근.
- 결정·이유: PostgreSQL을 원본 저장소로 사용하고 기본 저장·조회는 Spring Data JPA로 구현한다. 집계 등 필요한 쿼리는 Data 계층에서 직접 SQL로 표현할 수 있다. 스키마 변경은 Flyway로 관리해 개발·검증 환경을 재현한다.
- 단점·재검토 조건: JPA가 생성하는 쿼리와 영속성 동작을 학습해야 하고, 직접 SQL은 PostgreSQL에 의존할 수 있다. 실측 병목에 따라 개별 조회 구현을 개선하되 저장소 교체는 별도 근거를 검토한다.

## ADR-003 · 2026-10-11 · 웹 로그인은 서버 세션으로 시작

- 상태: 채택
- 맥락·제약: 구매자·판매자 웹이 초기 대상이며 주문·집계 검증이 주요 학습 목표다. 사용자는 JWT·OAuth2·Redis·RTR 구현 경험이 있지만 이번 초기 범위에는 세션을 선택했다.
- 대안: 서버 세션, JWT와 갱신 토큰·Redis 저장, 외부 계정 로그인.
- 결정·이유: Spring Security 세션으로 로그인·로그아웃과 구매자·판매자 인가를 구현한다. 별도 React 화면은 동일 출처 API 경로를 사용하고 쿠키·CSRF 보호를 구성한다.
- 단점·재검토 조건: 메모리 세션은 서버 재시작 시 소멸하고 여러 서버가 공유하지 못한다. 서버 확장 실험 시 Redis 세션 공유를, 외부 계정 로그인 요구 시 OAuth2/OIDC를 별도로 검토한다. 세션에서 JWT로의 변경은 자동 전환이 아니라 별도 인증 계약 변경이다.

## ADR-004 · 2026-10-12 · 날짜별 판매 조건과 매장 공통 수령 시간

- 상태: 일부 대체. 날짜별 상품·공통 시간과 잠금 구조는 유지한다. 판매 일정·삭제·복구 제약은 ADR-005, 통합 표·판매 중단·일괄 적용은 ADR-006을 따른다. 아래는 당시 결정 기록이다.
- 맥락·제약: 상품명은 자유 입력이고 판매 구성은 숫자로 받는다. 상품별 수령 시간이 달라지면 한 번에 수령하는 매장 주문의 시간 계약이 모호해진다. Phase 3에는 주문이 없지만 등록·수정 간 무결성은 필요하다.
- 대안: 상품별 시간 중복 저장, 매장·날짜별 공통 시간. 상품별/매장별 수정 잠금, 낙관적 버전 검사.
- 결정·이유: 상품 기본 정보·날짜별 판매 조건·매장 날짜별 수령 시간을 분리한다. 외래 키·고유 제약으로 상품당 날짜별 하나의 제안을 유지한다. 기존 JPA 계정·매장은 유지하고 신규 Data에서는 관계 조회와 PostgreSQL upsert를 JdbcTemplate으로 표현한다. Business 트랜잭션에서 소유권 검사 후 매장 행을 잠그고, 잠금 획득 후 한국 시간 날짜를 재검사해 자정 경계와 동시 등록·수정의 부분 반영을 방지한다. 잠금은 상품명/판매 구성 고정 검사와 제안 등록도 직렬화한다.
- 단점·재검토 조건: 같은 매장의 변경 요청이 직렬화된다. 가격·수량 수정은 잠금 순서에 따른 마지막 요청이 적용된다. Phase 4의 주문·재고 확보 계약을 확정할 때 잠금 범위·수량 변경·예약 이후 수령 시간 변경을 재검토한다. 이번 잠금은 주문 정확성을 보장한 것으로 취급하지 않는다. 추가 테이블만 생성하므로 V1 데이터는 변경하지 않으며 복구 시 신규 테이블 데이터를 백업하고 이전 앱으로 되돌릴 수 있다.
- 요구사항: [Spec](../SPEC.md)의 Phase 3 계약.

## ADR-005 · 2026-10-13 · 확보 재고의 당일 판매와 기록을 보존하는 상품 삭제

- 상태: 채택. 판매 일정은 ADR-004의 전날 예약 전제를 대체하며 매장·날짜별 공통 시간과 변경 잠금은 유지한다.
- 맥락·제약: 도매 매입·납품을 예측하는 범위를 제외하고 판매자가 확보한 재고로 당일 판매한다. 현장 재고 자동 연동은 제외하되 온라인 수량과 판매 실패 처리는 서비스 책임이다. 상품 삭제 요구가 추가되었고 향후 주문·판매 이력 참조를 보존해야 한다.
- 대안: 전날 주문 후 매입, 확보 재고의 당일 판매. 모든 매장 동일 마감, 매장별 마감. 상품 물리 삭제, 기록을 남기는 삭제.
- 결정·이유: 한국 시간 오늘 수령분만 수동 공개한다. 판매자가 매장·날짜별 주문 마감을 정하며 수령 시작보다 늦을 수 없다. 공개 조회와 판매 조건 변경은 마감 정각부터 중단한다. 상품은 archived_at을 기록해 목록·공개 판매에서 제외하고 기존 상품·판매 제안 행은 보존한다. 매장 잠금으로 삭제·수정·공개를 직렬화한다.
- 단점·재검토 조건: 매장별 마감 차이는 카드·상세의 명시적 안내와 Phase 4의 전체 장바구니 마감 검증이 필요하다. 현장 판매와의 수량 차이는 자동 감지하지 못하며 판매 실패로 처리한다. 당일 수령의 준비 시간은 판매자가 주문 마감과 수령 시작으로 확보한다. 실제 POS 연동이나 사전 예약 요구가 생기면 재검토한다.
- 호환성·복구: 기존 V1·V2 마이그레이션은 수정하지 않는다. V3·V4에서 삭제 표시와 주문 마감을 추가하며 기존 마감 값은 수령 시작으로 채운다. 시간 저장 API에 orderDeadline이 필수가 되어 기존 요청은 400이다. 적용 전 DB를 백업한다. 이전 앱은 삭제 표시를 무시하므로 운영 DB에 그대로 되돌려 공개하면 안 된다. 복구는 서비스를 중지하고 적용 전 백업을 별도 DB에 복원해 검증한 후 이전 앱과 연결한다. 새 판매 데이터를 보존하려면 복구 전 별도로 백업한다.
- 요구사항: [Spec](../SPEC.md)의 당일 판매 변경 수용 기준. 주문·결제 구현은 Phase 4 범위다.

## ADR-006 · 2026-10-13 · 통합 판매 표와 원자적 일괄 적용

- 상태: 채택. 사용자 확정한 오늘 판매 중단·전체 미적용 정책을 따른다.
- 맥락·제약: 여러 상품의 가격·수량을 한 화면에서 편집하고 공통 시간을 함께 적용해야 한다. 기존 단건 API 반복 호출은 중간 실패 시 일부만 반영된다. 상품 삭제와 하루의 판매 중단을 구분하고 판매 이력을 보존해야 한다.
- 대안: 단건 요청 반복과 부분 성공 안내, 단일 일괄 적용 트랜잭션. 판매 행 삭제, 활성 여부 별도 기록.
- 결정·이유: 공통 시간과 변경한 최대 100행을 하나의 Business 트랜잭션으로 처리한다. 기존 매장 행 잠금·잠금 후 날짜 검사와 마감 규칙을 유지한다. active 상태로 오늘 판매 중단을 나타내며 물리 삭제·수량 0 처리와 구분한다. 판매자 조회는 본인 상품과 당일 판매 조건을 함께 반환해 공개 검색을 상품별로 반복하지 않는다.
- 단점·재검토 조건: 같은 매장의 변경을 직렬화하며 마지막 성공한 변경이 적용된다. 한 행의 오류가 전체를 차단한다. Phase 4 주문 이후 수량·시간 변경 제한과 충돌 검사를 다시 확정한다.
- 호환성·복구: V5에서 daily_offers.active를 true 기본값으로 추가해 기존 공개 상태를 유지한다. 기존 단건 판매 저장은 다시 활성화하며 공개 검색·상세는 active를 검사한다. 이전 앱은 중단 상태를 무시하므로 V5 적용 DB에 이전 앱을 직접 연결하지 않는다. 적용 전 백업·별도 DB 복원 확인 후 갱신하고, 복구 시 중지·백업 복원·이전 앱 연결 순서를 따른다.
- 요구사항: [Spec](../SPEC.md)의 통합 표·일괄 판매 수용 기준.

## ADR-007 · 2026-10-13 · 선점 없는 모의 결제와 PostgreSQL 매장 행 잠금

- 상태: 채택. 사용자 요청으로 5분 확보 초안을 대체한다. ADR-004·ADR-006의 기존 매장 잠금을 주문 확정과 판매자 변경에도 공유하며, Phase 4의 주문 동시성 검증은 새로 수행한다.
- 맥락·제약: 재고 선점 없이 먼저 결제를 확정한 요청이 구매해야 한다. 같은 마지막 상품의 중복 성공, 여러 매장 부분 차감, 판매자 절대 수량 저장에 의한 차감 덮어쓰기를 막아야 한다. 현재 단일 Spring 서버·PostgreSQL과 모의 결제가 대상이며 Redis 의존성·설정은 도입되어 있지 않다.
- 대안: (1) 만료 시간이 있는 사전 재고 확보: 결제 중 물량을 보호하지만 사용자가 원하지 않는 선점·만료·반환이 추가된다. (2) PostgreSQL의 잠금·트랜잭션으로 최종 확정: 기존 판매자 잠금과 같은 저장소에서 전체 원자성을 유지할 수 있다. (3) Redis 분산 락 추가: 여러 실행 주체의 DB 밖 공유 자원까지 조율할 수 있지만 Redis 가용성·락 소유권·만료·지연된 소유자의 쓰기 방지와 DB 무결성을 별도로 다뤄야 한다.
- 결정·이유: 사전 재고 선점 없이 최종 처리에서 전체 재고 검사·차감·모의 결제 성공 기록·주문 저장을 같은 DB 트랜잭션으로 확정한다. 기존 stores 행의 FOR UPDATE 잠금을 사용하며 여러 매장은 ID 오름차순으로 획득한다. 잠금을 얻은 뒤 현재 조건을 재검사한다. 판매자 수량 변경은 같은 잠금과 재고 버전 검사에 참여한다. 같은 요청의 재시도는 영속 결과와 고유 제약으로 한 번만 확정한다. 모의 지연·응답 대기는 트랜잭션 밖에서 재현해 잠금을 유지하지 않는다. 모의 결과가 DB에 함께 저장되기 때문에 가능한 계약이며 외부 결제 원자성을 주장하지 않는다.
- Redis 미도입 이유: 여러 구매자가 경쟁한다는 사실이나 품절 실패 건수만으로 Redis가 필요해지지 않는다. 재고 1개에 여러 요청이면 성공 1건·품절 실패 나머지가 정상이다. 같은 PostgreSQL을 쓰는 서버가 여러 대가 되어도 DB 행 잠금은 서버 간 요청을 조율한다. 분산 락이 품절 실패를 없애거나 결제·DB를 원자적으로 만들지는 않는다.
- 단점·재검토 조건: 매장 전체 변경이 직렬화되어 서로 다른 상품도 같은 매장이면 대기할 수 있으며 클릭·요청 도착 순서의 공정성은 보장하지 않는다. 잠금 대기·timeout·deadlock은 품절과 구분한다. 실제 부하에서 대기 시간·처리량·실패 원인을 측정한 뒤 트랜잭션 길이·SQL·잠금 범위를 우선 검토한다. DB 트랜잭션으로 보호할 수 없는 공유 자원·여러 저장소의 작업 조율이 생기거나 실측 병목 근거가 있으면 Redis 등 대안을 별도 ADR로 재검토한다. 서버 수 증가나 인기 상품의 품절만으로 자동 도입하지 않는다.
- 호환성·실패 처리: 재고 버전 조회·수량 저장 계약은 API·화면·OpenAPI·테스트를 함께 갱신한다. 기존 V1~V5는 수정하지 않고 추가 마이그레이션으로 기존 데이터를 보존한다. 저장 오류는 전체 롤백, 성공 후 응답 유실은 저장 결과 조회, 중복 요청은 동일 결과로 처리한다. 외부 실결제 도입 시 선승인 후 품절에 대한 취소/환불과 장애 복구 계약을 별도로 설계한다. DB 갱신 전 백업·별도 복원 확인과 기존 서비스 중지·복원 절차를 유지한다.
- 복구 결정·이유: 요청 준비 기록은 최종 확정과 별도 트랜잭션에 저장해 지연·저장 오류·서버 종료 후 결과를 식별한다. 확정은 기존 재고·주문 트랜잭션으로 모두 적용하거나 모두 롤백한다. 진행 요청의 재시도 이력을 영속화해 오류 요청이 다른 요청의 복구를 계속 앞에서 막지 않게 한다. 조회 API는 복구 실행과 분리하고 변경 요청의 CSRF 계약을 유지한다. 복구 트랜잭션도 같은 구매자·매장 잠금에 참여한다.
- 검증 요구: 실제 PostgreSQL에서 마지막 재고 다자 경쟁·여러 매장 부분 실패 롤백·판매 저장 경쟁·시간 변경 경쟁·동일 요청 동시 재시도·모의 실패·지연·성공 후 응답 유실·재기동 결과 조회를 검증한다. 이 결정 기록 자체는 구현 또는 성능 검증 완료 증거가 아니다. 기존 계층·의존성 gate는 유지하며 신규 공개 Business 진입점의 호출 방향과 순환 금지를 검증한다.
- 요구사항: [Spec의 Phase 4 계약](../SPEC.md). 남은 구현·검증은 `PLAN.md`(프로젝트 루트의 로컬 계획)을 따른다.

## ADR-008 · 2026-10-15 · 관리자 초기 생성과 원자적 운영 변경 이력

- 상태: 채택. Phase 4.5 인터뷰에서 확정한 관리자 1명·신규 매장/판매자 동시 등록·이력 조회 계약을 따른다.
- 맥락·제약: 공개 관리자/판매자 가입 없이 운영 준비가 가능해야 한다. 계정만 남거나 이력 없이 관리 정보만 바뀌면 운영 추적이 어려워진다. 기존 판매자·주문·데모 데이터는 보존해야 한다.
- 대안: 공개 관리자 가입 또는 화면 내 관리자 추가, 명시적 초기 설정 1회 생성. 업무 테이블에 최근 변경만 저장, 별도 이력 테이블에 전후 값 누적. 업무 변경 후 이력 비동기 저장, 동일 DB 트랜잭션 저장.
- 결정·이유: 관리자 생성은 명시적 초기 설정으로만 활성화한다. DB 고유 인덱스로 관리자 1명을 제한하며 재기동은 기존 관리자의 비밀번호·이메일을 덮어쓰지 않는다. 관리자 업무 모듈의 Business가 계정·매장·상품·주문의 공개 Business 진입점을 호출한다. 업무 변경과 별도 관리자 이력은 하나의 PostgreSQL 트랜잭션으로 저장해 이력 실패도 전체 롤백한다. 이력에는 인증 정보를 넣지 않는다.
- 동시성: 시장 이름 수정·매장 등록은 대상 시장 행, 매장 이름 수정은 기존 판매/주문과 같은 매장 행, 담당자 수정은 판매자 계정 행을 잠근다. 계정 ID·정규화 이메일·소유자 고유 제약을 유지한다. 기존 주문에 저장한 매장 이름·가격·수령 조건은 수정하지 않는다.
- 호환성: V1~V6는 변경하지 않고 V7에서 ADMIN·담당자 정보·첫 비밀번호 변경 여부·이력을 추가한다. 기존 계정은 비밀번호 변경 강제 없이 유지하며 누락 담당자는 관리자가 보완한다. 신규 판매자만 첫 비밀번호 변경 전 업무를 차단한다. 권한은 요청마다 현재 제한을 확인하고 관리자에게 구매자/판매자 권한을 상속하지 않는다.
- 단점·재검토 조건: 관리자 1명 정책과 직접 비밀번호 전달은 운영 인원 증가·실서비스 도입 시 재검토한다. 연락처는 미인증 정보이며 신원 확인·계정 복구 근거가 아니다. 동기 이력 저장 장애는 관리 변경을 차단하며, 현재 규모에서 별도 큐·감사 저장소를 도입하지 않는다.
- 복구: 시연/운영 DB 갱신 전 백업·별도 복원 검증을 수행한다. 이전 앱은 ADMIN과 첫 비밀번호 제한을 이해하지 못하므로 V7 DB에 직접 연결하지 않는다. 복구는 앱 중지 → 신규 데이터 별도 백업 → 갱신 전 백업을 별도 DB에 복원·확인 → 이전 앱 연결 순서다. 이번 구현 검증은 독립 테스트 DB에서만 수행한다.
- 요구사항: [Spec의 관리자 운영 계약](../SPEC.md). 실행 설정·검증 절차는 [README](../README.md), 구현 상태는 로컬 PLAN을 따른다.

## ADR-009 · 2026-10-16 · 시장 후보 스냅샷과 운영 시장의 분리

- 상태: 채택. 위치 기능 추가 인터뷰의 확정 계약을 따른다.
- 맥락·제약: 공공자료로 시장 등록을 돕되 입점하지 않은 시장이 구매자에게 노출되면 안 된다. 외부 지도 장애에도 DB 목록·기존 구매를 유지하고, 기존 시장 ID·매장·주문을 보존해야 한다. 원본의 누락·오타·행정구역 개편을 실제 운영 정보에 자동 적용할 수 없다.
- 대안: 공공 API 실시간 목록, 모든 공공시장을 운영 시장으로 최초 등록, 별도 후보 스냅샷에서 관리자 확인 후 등록. 시장명 전국 유일, 지역과 이름의 조합으로 유일성 제한. 대표 주소와 표시점을 항상 동기화하거나 독립적으로 관리.
- 결정·이유: 공식 자료를 별도 후보 테이블에 버전 마이그레이션으로 한 번 적재하고 등록 시장과 연결하지 않는다. 후보 선택은 입력 보조이며 등록에는 관리자 확인·필수 정보 검증이 필요하다. 등록 시장은 기존 ID를 유지하고 공식 지역 코드·대표 주소·표시 좌표를 추가한다. 시장명은 같은 시군구에서만 유일하며 기존 위치 미등록 시장은 별도 고유 인덱스로 호환한다. 참고 주소 조회는 대표 주소를 변경하지 않는다.
- 의존성: 기존 store 기능의 Business→Data 경계를 유지한다. 관리자 모듈은 store의 공개 Business 진입점으로 등록·수정·후보를 조회하고 기존 원자적 변경 이력 트랜잭션을 유지한다. 네이버 SDK는 프런트 API 영역에 격리하며 서버 목록·후보 저장은 SDK나 외부 네트워크에 의존하지 않는다. 내 주변은 저장된 표시 좌표의 직선거리 계산이며 사용자 위치를 DB에 저장하지 않는다.
- 단점·재검토 조건: 후보 스냅샷은 최신성을 자동 보장하지 않고 일부 누락값은 관리자 보완이 필요하다. 지역 개편·후보 갱신은 새 자료의 매핑·호환성을 검토한 별도 변경으로 처리한다. 현재 규모에서는 조회 대상이 소수인 등록 시장을 메모리에서 거리순으로 계산하며, 실측 병목이 생기면 공간 인덱스를 검토한다.
- 호환성·복구: V1~V7은 수정하지 않고 V8~V9로 위치·기준표·후보를 추가한다. 기존 시장은 위치 미등록으로 보존한다. 기존 주문 스냅샷을 갱신하지 않는다. 운영 DB 적용 전 백업·별도 복원 확인을 수행하고 복구 시 앱을 중지한 뒤 갱신 전 DB를 별도 복원해 이전 앱을 연결한다. 수동 테스트 DB는 검증 중 임의 초기화하지 않는다.
- 요구사항: [Spec의 시장 위치 계약](../SPEC.md#시장-위치와-지역별-선택-추가-계약). 원본·변환 기준은 [후보 출처](market-catalog-sources.md), 구현·검증 상태는 로컬 PLAN을 따른다.

## ADR-010 · 2026-10-19 · 주문 운영 상태와 영속 모의 환불 복구

- 상태: 채택. Phase 5 사용자 인터뷰에서 일반 취소·수령 시간·미수령·예외 환불·매장 제보 범위를 확정했다.
- 맥락·제약: 통합 결제 후 매장별 일부 상품 판매 실패, 나머지 취소, 수령과 취소 경쟁, 환불 재시작 복구가 필요하다. 결제 성공 사실과 주문 이행·환불 결과는 다른 의미이며 기존 주문 스냅샷을 보존해야 한다.
- 대안: 결제 상태를 취소 상태로 덮어쓰기 또는 매장 주문/항목의 이행 상태와 환불 작업 분리. 취소와 환불을 하나의 즉시 성공으로 처리하거나 영속 작업에서 결과를 복구. 신규 주문 운영 모듈 또는 기존 주문 소유 모듈 확장.
- 결정·이유: 기존 주문 소유 모듈인 checkout을 확장하고 결제 성공 사실과 주문 이행·환불 결과를 분리한다. 취소와 환불 의무는 함께 확정하되 제공자 결과는 별도로 영속화한다. 제공자 성공 후 응답 유실이나 로컬 완료 실패에도 취소를 되돌리거나 중복 지급하지 않고 기존 결과로 복구하기 위해서다. 재시도에는 임대와 시도 식별자를 사용해 중단된 작업을 회수하고 이전 시도의 늦은 실패를 배제한다. 지속 실패는 자동 반복 대신 관리자 확인으로 전환한다. 실제 PG의 원자성은 주장하지 않는다.
- 동시성: 취소·재고 반환·결제·운영 중지는 기존 매장 잠금을 공유한다. 서로 다른 잠금 기준을 추가해 판매 수량이나 구매 가능 상태가 엇갈리는 것을 막기 위한 선택이다. 기존 결제의 잠금 방향을 역전하지 않고 매장 순서를 일관되게 유지해 교착을 피한다. 매장 내 직렬화 비용을 수용하며 재고 변경의 소유권은 product에 유지한다.
- 운영 중지: 제보·운영 상태는 store가 소유하고 admin이 각 기능의 공개 Business 진입점을 조합해 업무 변경과 관리자 이력을 함께 확정한다. 주문 기능이 admin을 역참조하지 않아 모듈 순환을 피하며, 제보 판단과 기존 주문의 보상 처리는 독립적으로 유지한다.
- 단점·재검토 조건: 매장 내 처리는 직렬화되고 영속 환불 작업·모의 결과가 추가된다. 수령 마감은 현재 시각으로 판단해 배치 지연에도 수령을 차단한다. 실결제 도입 시 제공자별 조회·멱등키 유효기간·실패 분류·웹훅·대사 정책을 별도 검토한다. 구매자 미방문은 보관·재판매 기회 비용이 있어 자동 환불하지 않으며 매장 귀책·서비스 오류는 관리자 확인 후 예외 환불한다.
- 호환성·복구: 기존 주문과 환불 의무를 임의로 다시 해석하지 않고 보존한다. 수령 코드 충돌 보정도 이미 발급된 비충돌 코드를 유지해 구매자 혼란을 줄인다. 이전 앱은 새 주문 상태를 이해하지 못하므로 갱신 DB에 직접 연결하는 복구는 허용하지 않는다. 실제 갱신·복원 절차는 README를 따른다.
- 요구사항: [Spec의 Phase 5](../SPEC.md#phase-5--취소환불-운영-확정-계약). 실행·검증 상태는 로컬 PLAN을 따른다.
